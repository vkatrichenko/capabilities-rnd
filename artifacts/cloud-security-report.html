Industry standards — and why they matter

In plain words: this is the marking scheme. Amazon publishes a list of security basics for a small organisation running on its cloud; the table below is that list plus the industry additions for containers and AI, with our own status against each line.

The yardstick is the AWS Startup Security Baseline (SSB): foundational controls for a single-account architecture, aligned to the Well-Architected security pillar — which is what several projects sharing account 941000539201 are. Vendor guidance (Wiz, Sysdig, Snyk, Palo Alto, Spacelift) fills in the container, IaC-scanning and identity detail; the AWS AI Security Framework covers the Bedrock surface; Prowler's own mappings score the live account against CIS 5.0 and the Well-Architected pillar. Status reflects the strongest implementation in the org; per-repo scores are in HOPS implementation.

Why these five groups

  • Identity and OIDC — the pipeline is the most privileged identity in the org and the one an attacker reaches through a pull request; humans and workloads come next. SSB ACCT.02–.05, ACCT.13, WKLD.01; OWASP CI/CD Top 10 CICD-SEC-2.
  • Data protection and workload hardening — what is at rest (the database, the buckets, the Terraform state that holds every secret in cleartext, the secret store) and what runs (pod security standards, non-root images, scan-on-push, immutable tags, pinned tooling). SSB ACCT.08, WKLD.03/.04/.08/.09; CIS EKS §4; Sysdig's container practices.
  • Network — private subnets, security groups, TLS at the edge, VPC endpoints, and whether the cluster's own API is reachable from the internet. SSB WKLD.10–.14; CIS EKS 5.4.
  • Detection and governance — CloudTrail, GuardDuty, Config, Security Hub; account hygiene (root MFA, password policy, Access Analyzer); a scanner in the pipeline; tags; toolchain currency; an audit that can see any of it. SSB ACCT.06/.07/.11/.14/.15, WKLD.15.
  • AI workload on AWS — the part specific to this initiative: Bedrock invoke scoping, guardrails, invocation logging, PrivateLink, cost alarms. AWS AI Security Framework.

HOPS — how secure is the infrastructure, per repository

In plain words: one row per code repository, with a percentage for how many of the 23 security basics it has. The method behind the percentage, and every check explained without jargon, is in How we score.

Three numbers per repo, three meanings, none of them "how secure" alone. Coverage follows the AWOS audit's own convention — awarded ÷ applicable over the same 23-control list for every repo, pass = 1, partial = ½, fail = 0, not-applicable excluded — and scores what the standards ask for, including what no scanner reads (CI identity, human access, audit cadence). Trivy pass-rate is the scanner's own successes ÷ evaluated, weighted by how many resources exist — high everywhere because most resources are fine and the seams between them are not resources. Prowler is the live account. Judgement and evidence for every cell: research/baseline/cloud-control-scores.md.

Layer 4 — process

An accepted-risk register (docs/processes/security-notes.md) that already records the in-cluster plain-HTTP decision; an agent guard that blocks reads of ~/.aws and credential files; a rule that bans curl | sh in hooks — which the deploy workflows do. No document on cluster architecture, network design, encryption at rest, KMS, backups, DR, incident response or a threat model (audit AS-11 says the same). The GitLab migration was a file copy: three IaC repos with GitLab MR templates, no .github/, READMEs pointing at the old host.

What makes this the blueprint The skeleton is right and the seams are open. Every control that is present is a small declarative setting in a module; every gap is the same kind of setting, absent — scan_on_push, rds.force_ssl, runAsNonRoot, endpoint_private_access, one service_role_arn per project. The capability is the pipeline and the shared modules that make the present ones the default and the absent ones impossible to forget.

How we score — and what "finished" would look like

This section is written for a reader who does not work with this system every day. It explains where the percentages come from, what each thing we check actually means, and what our infrastructure would look like if none of it were missing.

The short version We wrote down 23 things that well-run cloud infrastructure does. We checked each of our seven code repositories against every one of them, gave a point for done, half a point for half-done, nothing for not done, and skipped the ones that do not apply to that repository. The percentage is points scored ÷ points available. It is a building inspection, not an exam grade: 30 % does not mean the system is broken, it means most of the safety features an inspector looks for have not been installed yet.

The method, in four steps

  1. One list for everybody. The same 23 checks are applied to every repository, grouped into the five areas this report uses: who can get in, what protects the data and the running software, the network, whether anyone would notice a problem, and the AI-specific controls. The list comes from Amazon's own baseline for a small organisation on AWS, plus the industry standards named in Industry standards — we did not invent the bar.
  2. Three verdicts per check. Done (1 point) means the protection is in place and written down in the code, so it cannot quietly disappear. Half done (½ point) means it is partly there — protecting one environment but not the other, or switched on by hand where a person could switch it off again. Not done (0 points) means it is absent.
  3. Skip what does not apply. A repository with no database is not marked down for failing to encrypt one. Skipped checks are removed from the total, which is why the denominators differ: the platform repository is judged on 19 checks, the HOPS infrastructure repository on 21, a small service repository on 6 or 7.
  4. Divide, and keep the evidence. Every verdict carries the file and line it was read from, at a recorded version of the code. The full list of verdicts and their evidence is in the research files; nothing in the score is a matter of opinion that cannot be checked.

Why three different numbers, and not one

The report shows each repository's coverage beside two machine-produced numbers. They measure different things and they are supposed to disagree.

Coverage (29–41 %)

Judged against the 23 checks. It includes the things no tool can see: who holds the keys, whether a human can delete production, whether anyone reviews a change. This is the number to act on.

Scanner pass-rate (68–95 %)

Measured by a tool reading the code. It counts settings on resources — encryption on, logging off — so a repository with hundreds of correct settings and one shared master key scores high. Useful, but blind to the biggest risks in this report.

Live account (72.5 %)

Measured against the real AWS account, not the code. It is the only way to learn what someone switched on by hand — and therefore what could be switched off again without a trace.

A single blended figure would hide exactly the disagreement that matters. The clearest example in this report: one repository scores 76 % with the scanner and is one merge away from full administrator access to the production cluster. The scanner cannot see that. The coverage score can, because a human read the identity policy and marked it.

What "finished" would look like

If every check were green, this is what would be true. It is deliberately written as a picture rather than a list of settings, because that is the thing to aim at.

Getting in

Each project's pipeline has its own identity, which exists in code and can be read by anyone reviewing it. That identity can push its own images, deploy its own applications and read its own settings — and nothing else. It proves who it is per job and the proof expires in minutes. A change in the smallest project cannot reach the largest one. People reach production through a time-limited request with a second factor, and the account's master login is protected by a hardware key that lives in a safe. Nobody, human or machine, is a permanent administrator.

Data and running software

Every database is encrypted with a key we control, refuses unencrypted connections, and cannot be deleted without deliberately removing the protection first. Every storage bucket is closed to the public, encrypted and refuses unencrypted connections, and those three facts are written in the code rather than left to defaults. Passwords live in the vault, rotate on a schedule, and the rotation reaches the running system automatically. Containers run as an ordinary user on a read-only disk with no ability to gain privileges. Every image is scanned when it is published, and a published version can never be replaced by different content.

The network

The cluster's control panel is reachable only from our own network. Applications sit on private networks and talk to Amazon services over private routes with rules about what may travel them. Everything public is encrypted with a current standard and sits behind a filter. Network traffic records are on, so an investigation has something to read. Engineering tools — trace viewers, dashboards, metrics — are on the internal network behind the company login, not on the public internet behind a shared password.

Noticing and keeping it that way

Activity recording and configuration history keep coming from the IT department, and we can name who owns them. Threat detection, the security dashboard, the permission analyser and network traffic records are on too, each with an owner — either inherited from IT or described in our own code, so that switching one off is a visible change somebody has to approve. Our own account holds no duplicate, half-configured copy of something IT already does properly. Every infrastructure change is previewed for a human and machine-checked before it can apply; a change that would remove one of these protections fails the check. Every resource carries its owner. Alarms reach a named person with a written procedure. And a recurring audit measures all of it, so the score moves on a schedule instead of when someone remembers.

The AI parts

The AI service may call only the models we approved, over a private route. Prompts and answers are recorded, and a filter sits in front of them. Usage alarms are per project rather than account-wide, so one team's spike does not page another team.

What it would take Most of the distance is not exotic. A large share of the checks are a one-line or one-file change once someone decides to make it — switch on image scanning, require encrypted database connections, mark the secrets as secret, set the container user. Four are genuinely structural: splitting the shared deploy identity, closing the cluster's public control panel, giving the secret store per-project scope, and putting a review-and-check pipeline in front of every infrastructure repository. Those four are what the task list calls Blocks A and B, and they are the ones that stop the others from decaying afterwards.

Honest limits of this score

  • It is judged, not measured. A person read the code and assigned each verdict against a written definition. The evidence is recorded per verdict so anyone can disagree with a specific cell, which is the point — but two careful people could score a few cells differently.
  • Half a point is a blunt instrument. "Encrypted but with a shared key" and "encrypted but only in one environment" both score ½, and they are not equally serious.
  • Skipped checks flatter small repositories. A repository judged on six checks is not directly comparable to one judged on 21; the small ones are shown for completeness, and the numbers to act on are the platform and the two infrastructure repositories.
  • It is a snapshot. Every score names the exact version of the code it was read from. The point of the recurring audit in the task list is that this number should be produced automatically from now on, not by hand every few months.

How it happens — the vectors are infrastructure-shaped

  • One identity for everyone. Seven repositories' GitHub Actions jobs run as codebuild-hops-aws-iac: cluster-admin, iam:PassRole on *, image push to every registry, the prod database dump — and the webhook that starts a build checks only that a job was queued. A merge in the smallest repo is a merge into the largest blast radius.
  • The right mechanism with the wrong permission. barley federates CI by OIDC — textbook — and the last line of the policy list attaches AdministratorAccess.
  • Secrets that are never literals, and still leak. No live resource commits a credential. They leak through flags and scope: an External Secrets role that reads every parameter in the account, sensitive never used, a password as a GitHub variable posted in a URL, a DB password on a command line, changeme and adminpassword in values files, and six real credentials sitting in a dead module in git history.
  • Nobody owns the controls nobody inherited. The IT department provides the organization, single sign-on and two company-wide activity trails, and those are the parts that work. Bedrock logging and a guardrail were switched on locally by hand and are declared in no repository. GuardDuty, Security Hub, the permission analyser and network flow logs fall between the two — IT has not pushed them down and no project has asked for them, so they are simply off.
  • Good patterns and bad ones land at the same rate. The 42 commits since the retired GitLab head added provider tags, two model buckets and an S3 endpoint — and s3:* on a bare bucket, a wider wildcard trust, three more unscanned registries, and deleted the CI-variable pipeline with nothing in its place. Without a scanner in the loop there is no ratchet.
  • Production data leaves production. The nightly dump lands in a bucket declaring nothing and is restored into demo environments on spot nodes, while the process doc says previews carry no production data.

Where four of these recommendations come from

T6, T-H2, T-I5 and T-I7 cite ignition-consultants (proj-ignition-consultants/ignition-consultant-ai, production account, reviewed read-only 2026-09-04). It is another Provectus project on AWS, and on four points it is materially ahead of HOPS: it declares its detective controls in a single named file, it routes severity-filtered Security Hub findings into Slack, it runs Terraform format, documentation, lint and misconfiguration scanning as pre-commit hooks with the scanner deliberately warn-only to start, and it backs resources up by tag rather than one plan per resource. Those four are proven inside the company rather than proposed from a standards document, which is the whole reason to prefer them.

Adopting a pattern is not endorsing the project: that review found its own serious problems, and they are not this report's subject. Two points are worth carrying across anyway. Where its version is incomplete — backup vaults with no lock and no cross-region copy — the task above says so and asks for the missing part. And the pipeline role at the centre of T3 is not a HOPS invention: the same role in that project grants 30 of the same 33 IAM actions, including iam:PassRole on *, and both node roles carry the identical six FullAccess policies. It is a shared internal template, which is precisely the argument for T-C1 — fix the module once and every project inherits the fix, exactly as they have all inherited the flaw.

Methodology — capability 1's rules, and what this one added

The eleven rules from the AI SDLC Security research were applied unchanged: inventory before scanning; same tool, same ruleset, same day; audit the audit, then read the auditor; root-cause the control, not the finding; prove an ignore rule narrow before trusting it; resolve the real base ref before measuring; run every gate against the input it must fail on, absence included; close from the default branch; log everything as it happens. Five were earned here:

  1. Enumerate the org's repositories before trusting a pointer. The first draft measured the HOPS IaC from a GitLab clone named in a README; the org had moved to GitHub, the real head was 42 commits ahead, and the platform repository had never been read. gh repo list is now the first command, before the first file.
  2. Resolve which repository owns the resource before scoring its absence. The project IaC creates no VPC, cluster or OIDC provider — core-infra does. "Absent in repo" and "absent" are different verdicts; the live-account scan is the tie-breaker for what exists by hand.
  3. Render before you scan, and fail on nothing scanned. Trivy reported 0 on a chart it could not render and said nothing about it. Every Helm surface was rendered with the values CI actually passes; the CI recommendation carries the rule.
  4. A configured linter that cannot load is a finding, not a pass. hops-infra's own .tflint.hcl produced two incompatibilities with any tflint since 2024 — evidence of non-execution that a file-existence check would score as present.
  5. Show three numbers, not one. Coverage (judged against the standard), scanner pass-rate (measured, resource-weighted) and the live account disagree by design; a single blended figure would hide which of them moved. Each is labelled with how it was computed, and the judged one carries its evidence per cell.
