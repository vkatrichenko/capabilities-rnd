Overview

For managers: we researched how to secure software development where AI writes most of the code, measured our own four internal repos against industry best practice, and proved — with our own data — that the controls work: the one project with a secret-scanning gate has a verifiably clean history since the gate; the comparable project without one accumulated 7 leaked credentials, one of which is still readable in the current tree. The result is a blueprint we can apply to every future project and present to clients as our AI-coding & CI/CD security capability.

The thesis At ~80% AI-authored code the industry answer (Anthropic) is not more human review — it is automatic checks that give the same verdict every time, review agents with one narrow job and mandatory evidence, and logged accountability. Our own repos prove both sides: with the first layer installed, leaks stop; without it, they accumulate — one is sitting in the current code right now, and six more remain readable in git history. The gap is the capability story.

Industry standards — and why they matter

Each group below is an attack surface specific to AI-assisted development. The table maps the industry-consensus practice to what we implement today. Status reflects the strongest implementation in the org; per-repo variance is in Gaps & roadmap.

Why these five groups

  • Secrets — LLM-generated code and AI workflows move credentials into places code review never looks: recorded test data (saved API responses that tests replay), committed reports, the coding agent's own configuration. Every leak we found was in one of those, none in application source.
  • AI-generated code — 45% of AI-generated code contains vulnerabilities and the rate has not improved across model generations (Veracode). Deterministic gates, not better models, are the control.
  • Supply chain — 19.7% of packages recommended by LLMs don't exist; attackers pre-register the names (USENIX 2025). Classic typosquatting defenses don't cover this.
  • AI toolchain — the agent's plug-ins (MCP servers) and the small scripts that run around its every action (hooks) execute with the developer's own privileges. One left at "whatever version is newest" is the same as downloading and running unreviewed code at every session start (CSA, OWASP Agentic ASI01).
  • Governance — controls decay without a loop: recurring audits, accepted-risk registers, and findings that become instruction-file updates (NIST SSDF, Anthropic).

The AWOS audit — what it covers, how it works

AWOS (Agentic Workflow Operating System) is Provectus's spec-driven development framework for Claude Code — product → roadmap → architecture → spec → tech → tasks → implement → verify, installed as a plugin. Its AI-readiness audit (/awos:ai-readiness-audit) is the diagnostic: a scored, evidence-backed assessment, recommended as the first step on any existing codebase, re-runnable on a cadence. Our projects store every run in context/audits/<date>/.

What it covers — 12 dimensions per run

Security (4 dimensions)

Application Security (OWASP ASVS 5.0) · Supply Chain Security · AI Security (agent files, skills, hooks, MCP configs) · Prevention Coverage (is the good state protected against regression?)

Engineering (5)

Delivery Flow (DORA) · Software Best Practices · Code Architecture · Quality Assurance · Documentation Quality

AI adoption (3)

AI Development Tooling · Spec-Driven Development · AI-SDLC Adoption (how AI-assisted the work actually is)

How it works

  • Detectors, not opinions. Each dimension is a set of checks (engine audit-core) with method detected or computed, run against collected sources: git history, CI config, code host, docs, tracker.
  • Every check carries evidence. Status (PASS/WARN/FAIL/SKIP), weight awarded vs max, an applies flag, a reliability/confidence tag, the standard it derives from (with version and URL), and an evidence array quoting the exact files and lines.
  • Scoring: dimension health = weight awarded ÷ applicable maximum ("coverage") — e.g. the hops 2026-08-03 run: overall 80.1%; ai-security 100%, supply-chain 96.2%, prevention 81.5%, app-sec 80%.
  • Machine-readable output: one JSON per dimension plus report.md/html and recommendations.md — which is what made the trend analysis and the blind-spot verification in this research possible.

Proof it drives change

The 07-17 → 08-03 hops runs show a working loop: PRV-01 (secret gate), AS-09 (rate limiting), AS-10 (authz), SCS-03 (pinning) all went FAIL→PASS, with the fixes' commits citing the audit finding IDs. Two dimensions gained 14–16 points in 17 days.

HOPS — the reference implementation

HOPS is the org's most-hardened repo and the change target for Phase 2. Five layers, verified 2026-08-14; for each, what it actually catches — not just what it claims.

Layer 1 — local (developer machine)

scripts/pre-commit: two-step scan of staged files — suspicious filename patterns (.env, .pem, keystores, credentials.json…) then content patterns. It warns but does not block, by design (a developer can bypass it with SKIP_SECRETS=1); the CI gate is documented as the enforcement layer behind it. Known limit: the filename pattern matches .env exactly and nothing else.

Layer 2 — agent-time (Claude Code)

A guard script runs before every file or shell action the coding agent takes (block-secrets.sh): the agent cannot read or write secret material at all. A second script runs after each action and re-installs the commit-time check — closing the "the check was never installed on this machine" hole for agent sessions. Note: these guard scripts live in scripts/claude-hooks/ — the folder the audit's AIS-03 check never looked in, and the one the agent-config-scan job below now reads from the settings that actually point at it.

The tuned config is the craft: .gitleaks.toml extends the default rules with an ignore-list of verified false alarms only — each entry excuses one specific harmless value, never a whole file or folder, so a real token in that same file still flags. The .env.example templates are deliberately not exempted. The current tree scans clean under this config; at factory settings, the same scanner produces 99.4% noise on a sibling repo.

Layer 4 — dependencies

Lockfiles for all npm/pnpm modules; gradle version catalog pins directs (no transitive lock yet); 115/121 deps exact-pinned; Dependabot (npm ×3, gradle, actions) with human review.

Layer 5 — process

CodeRabbit AI review with a tuned config; accepted-risk register (docs/processes/security-notes.md) recording the reasoning behind AS-01/AS-09 decisions so they aren't re-litigated; mandatory AWOS workflow; five audit runs on record with the measured 13-day remediation loop.

What makes this the blueprint Nothing here is exotic: each layer is a small, deterministic control wired into a stage of the workflow (commit → agent call → MR → dependency update → audit cadence). The evidence that the stack works is measured, not asserted — clean post-gate history, a 10× leak-rate difference vs the ungated sibling, and audit scores that moved when fixes landed.

How the leaks happen — the vectors are AI-SDLC-shaped

  • Recorded test data. Tests replay saved copies of real API responses. The cleaning step removed only the fields it had been told about, and GitLab's runners_token field was not on its list — so a live token was saved verbatim. A cleaner built as a list of known fields misses every field it has not seen yet.
  • Committed output files. A generated test report with a live bot token embedded in it.
  • Infrastructure config. Slack tokens typed straight into Terraform files, for 8 months.
  • The agent's own permission settings used as a secrets store. Live credentials pasted into Claude settings files — an AI-native vector no code scanner watches.

None of the 9 real-format leaks was in application source code. Defense-in-depth turns "the scrubber has a hole" into a non-event — hops has the backstop, barley does not.

Proof: a fake key planted on exactly such a line in hop-sync/Hubspot_data_sync.ipynb was reported 0 times under the shipped settings and 1 time after the fix. The same setting was separately seen dropping 3 genuine runner-token detections on barley even where the ignore rule matched nothing on the line at all — that second behaviour we could not reproduce in a clean test, so its root cause remains unconfirmed with the tool's maintainers.

This is the fourth variant of the pattern this capability keeps finding: a control can exist, be enforced, be wired up, be licensed — and still be scoped away by its own configuration, with no signal anywhere that detection was lost. The defence that generalises is procedural: compare what the scanner reports with and without its ignore-list, require every ignored finding to be explained by a named entry, and plant fake secrets in the ignored spots to prove the scanner still catches a real one there.
The gate we built to fix a "found nothing to check, so pass" bug shipped with the same bug FOUND IN REVIEW · FIXED BEFORE MERGE 2026-08-26
The whole point of roadmap item 9 is that the audit looked for a hooks folder that did not exist, skipped the check, and counted the skip as a pass — reporting 100%. Our replacement, pointed at a project with no agent settings file at all, printed "no agent hook surface in this repo — all clear" and reported success. A pull request that simply deleted or renamed the settings file would have turned the gate green.

Knowing the failure mode did not stop us rebuilding it. "Nothing to check" quietly becoming "pass" is not one tool's defect — it is the default shape of any check, and only running ours against an empty project exposed it. The fix is deliberately not a special case: "the thing I am supposed to scan is missing" is raised as an ordinary blocking finding, handled exactly like malicious hook content would be.

The same review found the next level of the same pattern. The new reviewer-assignment file covered the older guard scripts — the ones the audit already knew about — but not the new scanner itself or the pipeline job that runs it: a control that protected the previous generation of controls and not itself. Both paths added. The generalizable rule for the blueprint: every gate must be run against the input it is supposed to fail on, absence included, and its own source must sit inside the surface it protects.

Not every control is universal — item 8 is conditional on a practice

Item 8 applies to barley alone, and the reason generalises further than the fix does. Checked rather than assumed: hops saves no real API responses at all — none of the recording tools appear anywhere in it, and one is, in the team's own test comment, "deliberately not on the classpath." hops fakes its external services in code, so no response is ever written to disk. Running barley's own credential patterns across 2,537 hops test and fixture files returns zero credential-shaped values. sowinsights and hops-mcp record nothing either.

So this control attaches to a testing practice, not to a repository. The two projects made the same trade differently and neither is wrong:

  • barley saves real responses — its test data stays faithful to the live API, and every saved byte is potential credential material. It leaked exactly once, through the one field nobody had listed.
  • hops fakes the external service in code — structurally immune to this leak, at the cost of test data that can drift from the real API with no test noticing.

The blueprint should therefore carry this as a conditional control: the question a new project must answer is not "which language is this?" but "does this project save real API responses into committed files?" Copying barley's cleaner into hops would add maintained code that can never fire.

Two of our own controls collided — and the fix is the pattern

The new cleaning tests need fake credentials that look exactly like real ones, or they prove nothing — and the secret-scan gate merged four days earlier flagged them, correctly. Resolved by writing the marker NOTAREALTOKEN into the middle of each fake value and teaching the scanner to ignore that one string — ignored by value, never by folder, so a real token in that same test file still fires. Exempting the whole test folder would have been faster, and would have re-created the exact blind spot that made barley's own audit report a false "no secrets".

Methodology — repeatable for the next capability

  1. Inventory before scanning. Read what each repo already has (configs, CI, hooks, its own audits and accepted-risk registers) so findings are gaps, not rediscoveries.
  2. Same tool, same ruleset, same day. Cross-repo numbers are only comparable when the instrument is held constant — gitleaks 8.24.3 (the exact version the hops CI gate pins), default config for comparison, tuned config as a separate measurement.
  3. Full history, not just the current files. A committed-then-deleted secret is still in every clone. Findings classified as still-present vs history-only — the remedy differs (rotate + remove vs rotate).
  4. Triage by format confidence. High-confidence token formats (provider prefixes, PEM blocks) can't match by accident; loose regexes require manual review. Every reviewed with values masked; no credential tested for validity.
  5. Audit the audit — then read the auditor. Every surprising audit verdict re-verified against the repo by hand, which is how three detector blind spots were found; and before reporting one, traced to the line in the audit engine that produces it, confirmed on the maintainers' current default branch, and searched against their tracker for an existing report. A bug report that quotes the detector's own code is acted on; one that quotes the symptom is triaged.
  6. Root-cause the control, not the leak. The test-recording tokens were traced to the specific cleaner design (it removed only fields it already knew), producing a transferable pattern, not a one-off fix.
  7. Prove an ignore rule is narrow before trusting it. Added in Phase 2, after a tuned scanner config was found hiding real credentials. Every ignore-list is checked by re-running the scan without it; every ignored finding must be explained by a named entry; entries that match nothing are deleted rather than shipped; and fake secrets are planted inside each ignored spot to confirm a real one is still detected. An untested ignore rule is indistinguishable from a disabled check.
  8. Resolve the real base ref before measuring. Also added in Phase 2, twice earned: two measurements were taken against local clones 5 and 229 commits stale. Every number now states the ref it was measured at, by SHA.
  9. Run every gate against the input it must fail on — absence included. Added in Phase 2, after our own hook scanner was found reporting "all clear" on a repo with no agent settings file at all: the "nothing to check, so pass" failure it had been written to correct. A gate is now proved with a planted positive, a negative control on real code, and an empty input, and its own source is placed inside the surface it protects.
  10. Close an item from the default branch, not from the branch that was reviewed. Also Phase 2: re-deriving the claims from main after merge is what showed the portable copy of a shipped checker was two commits stale — it still carried the pass-when-broken version any second repo would have copied.
  11. Everything logged as it happens. Method log, findings, corrections (two of our own claims were caught and fixed by later evidence), and lessons — in the research repo, each number backed by a committed file.
