Overview

For managers: we researched how to secure software development where AI writes most of the code, measured our own four internal repos against industry best practice, and proved — with our own data — that the controls work: the one project with a secret-scanning gate has a verifiably clean history since the gate; the comparable project without one accumulated 7 leaked credentials, one of which is still readable in the current tree. The result is a blueprint we can apply to every future project and present to clients as our AI-coding & CI/CD security capability.

The thesis At ~80% AI-authored code the industry answer (Anthropic) is not more human review — it is deterministic gates, narrow-scope review agents with mandatory evidence, and logged accountability. Industry standards — and why they matter

Each group below is an attack surface specific to AI-assisted development. The table maps the industry-consensus practice to what we implement today. Status reflects the strongest implementation in the org; per-repo variance is in Gaps & roadmap.

Why these five groups

  • Secrets — LLM-generated code and AI workflows move credentials into places code review never looks: recorded test fixtures, committed reports, agent config. Every leak we found was in one of those, none in application source.
  • AI-generated code — 45% of AI-generated code contains vulnerabilities and the rate has not improved across model generations (Veracode). Deterministic gates, not better models, are the control.
  • Supply chain — 19.7% of packages recommended by LLMs don't exist; attackers pre-register the names (USENIX 2025). Classic typosquatting defenses don't cover this.
  • AI toolchain — MCP servers and agent hooks run with developer privileges. An unpinned one is curl | bash at every session start (CSA, OWASP Agentic ASI01).
  • Governance — controls decay without a loop: recurring audits, accepted-risk registers, and findings that become instruction-file updates (NIST SSDF, Anthropic).

The AWOS audit — what it covers, how it works

AWOS (Agentic Workflow Operating System) is Provectus's spec-driven development framework for Claude Code — product → roadmap → architecture → spec → tech → tasks → implement → verify, installed as a plugin. Its AI-readiness audit (/awos:ai-readiness-audit) is the diagnostic: a scored, evidence-backed assessment, recommended as the first step on any existing codebase, re-runnable on a cadence. Our projects store every run in context/audits/<date>/.

What it covers — 12 dimensions per run

Security (4 dimensions)

Application Security (OWASP ASVS 5.0) · Supply Chain Security · AI Security (agent files, skills, hooks, MCP configs) · Prevention Coverage (is the good state protected against regression?)

Engineering (5)

Delivery Flow (DORA) · Software Best Practices · Code Architecture · Quality Assurance · Documentation Quality

AI adoption (3)

AI Development Tooling · Spec-Driven Development · AI-SDLC Adoption (how AI-assisted the work actually is)

How it works

  • Detectors, not opinions. Each dimension is a set of checks (engine audit-core) with method detected or computed, run against collected sources: git history, CI config, code host, docs, tracker.
  • Every check carries evidence. Status (PASS/WARN/FAIL/SKIP), weight awarded vs max, an applies flag, a reliability/confidence tag, the standard it derives from (with version and URL), and an evidence array quoting the exact files and lines.
  • Scoring: dimension health = weight awarded ÷ applicable maximum ("coverage") — e.g. the hops 2026-08-03 run: overall 80.1%; ai-security 100%, supply-chain 96.2%, prevention 81.5%, app-sec 80%.
  • Machine-readable output: one JSON per dimension plus report.md/html and recommendations.md — which is what made the trend analysis and the blind-spot verification in this research possible.

Proof it drives change

The 07-17 → 08-03 hops runs show a working loop: PRV-01 (secret gate), AS-09 (rate limiting), AS-10 (authz), SCS-03 (pinning) all went FAIL→PASS, with the fixes' commits citing the audit finding IDs. Two dimensions gained 14–16 points in 17 days.

HOPS — the reference implementation

HOPS is the org's most-hardened repo and the change target for Phase 2. Five layers, verified 2026-08-14; for each, what it actually catches — not just what it claims.

Layer 1 — local (developer machine)

scripts/pre-commit: two-step scan of staged files — suspicious filename patterns (.env, .pem, keystores, credentials.json…) then content regexes. Advisory by design (SKIP_SECRETS=1 bypass); the CI gate is documented as the enforcement layer behind it. Known limit: filename pattern is anchored to .env exactly.

Layer 2 — agent-time (Claude Code)

PreToolUse hook on every file/shell tool → block-secrets.sh: the agent cannot read or write secret material at all. PostToolUse re-installs the git pre-commit hook — closing the "hook never installed" hole for agent sessions. Note: hooks live in scripts/claude-hooks/, which the audit's AIS-03 path assumption missed — and which the agent-config-scan job below now reads on the path the settings actually point at.

Layer 3 — CI (GitHub Actions, MR pipeline)

JobGatingDetail

osv-audit-hop-uiLABEL-GATED Runs only on PRs labeled frontend, covers hop-ui only — the gap is the trigger, not the tool

The tuned config is the craft: .gitleaks.toml extends the default ruleset with a verified-false-positives-only allowlist — value-level stopwords rather than path rules, so a real token in an allowlisted file still flags. .env.example is deliberately not path-allowlisted. Worktree scans clean under this config; untuned, the same scanner produces 99.4% noise on a sibling repo.

Layer 4 — dependencies

Lockfiles for all npm/pnpm modules; gradle version catalog pins directs (no transitive lock yet); 115/121 deps exact-pinned; Dependabot (npm ×3, gradle, actions) with human review.

Layer 5 — process

CodeRabbit AI review with a tuned config; accepted-risk register (docs/processes/security-notes.md) recording the reasoning behind AS-01/AS-09 decisions so they aren't re-litigated; mandatory AWOS workflow; five audit runs on record with the measured 13-day remediation loop.

What makes this the blueprint Nothing here is exotic: each layer is a small, deterministic control wired into a stage of the workflow (commit → agent call → MR → dependency update → audit cadence). The evidence that the stack works is measured, not asserted — clean post-gate history, a 10× leak-rate difference vs the ungated sibling, and audit scores that moved when fixes landed.

How the leaks happen — the vectors are AI-SDLC-shaped

  • Recorded test cassettes. Headers were filtered correctly; body scrubbing is a key denylist and GitLab's runners_token field wasn't on it. Denylists fail open on every new API field.
  • Committed artifacts. A test report embedding a live bot token.
  • IaC values pasted inline. Slack tokens in Terraform locals for 8 months.
  • Agent permission allow-patterns as a secrets store. Live credentials inside Claude settings allow-lists — an AI-native vector no code scanner sees.

None of the 9 real-format leaks was in application source code. Defense-in-depth turns "the scrubber has a hole" into a non-event — hops has the backstop, barley does not.

The finding that came out of shipping item 2: the hops gate was hiding secrets FIXED — PR #518 MERGED 2026-08-20
.gitleaks.toml used regexTarget = "line", which allowlists the entire line — so any real credential sharing a line with an allowlisted value was dropped. A synthetic HubSpot key planted on an allowlisted correlation-id line in hop-sync/Hubspot_data_sync.ipynb was reported 0 times under the shipped config and 1 time after the fix. The same setting was separately observed dropping findings when the allowlist regex matches nothing at all, costing 3 genuine GitLab runner-token detections on barley. Root cause unconfirmed upstream; not reproducible on synthetic fixtures.

This is the fourth variant of the pattern this capability keeps finding: a control can exist, be enforced, be wired up, be licensed — and still be scoped away by its own configuration, with no signal anywhere that detection was lost. The generalizable defence is procedural: diff every suppression config against a no-allowlist baseline, require each suppressed finding to be attributable to a named entry, and plant synthetic positives inside the suppressed contexts to prove the rule is narrow.
The gate we built to fix a skip-and-pass check shipped with the same defect FOUND IN REVIEW · FIXED BEFORE MERGE 2026-08-26
The whole point of roadmap item 9 is that AIS-03 found no .claude/hooks/ directory, skipped, and let the dimension report 100%. Our replacement, run against a directory with no .claude/settings.json in it, printed "no agent hook surface in this repo — all clear" and exited 0. A pull request that deleted or renamed the settings file would have turned the gate green.

Knowing the failure mode did not prevent rebuilding it. Skip-and-pass is not an upstream defect — it is the default shape of a check, and only running the tool against an empty directory exposed it. The fix is deliberately not a special case: an absent surface is pushed as an ordinary blocking finding, so it flows through the allowlist, the JSON output and the exit code exactly like malicious hook content does.

The same review found the second-order version one level up. The new CODEOWNERS routed review for scripts/pre-commit and scripts/claude-hooks/ — the guards the audit already knew about — but not for the scanner or the workflow that runs it: a control that protects the previous generation of controls and not itself. Both paths added. The generalizable rule for the blueprint: every gate must be run against the input it is supposed to fail on, absence included, and its own source must sit inside the surface it protects.

Not every control is universal — item 8 is conditional on a practice

Item 8 applies to barley alone, and the reason generalises further than the fix does. Checked rather than assumed: hops records no API traffic at all — no VCR, no cassettes, no nock recorder, and WireMock is, in their own test comment, "deliberately not on the classpath." hops stubs at the repository interface, so no response body is ever written to disk. Running barley's own credential patterns across 2,537 hops test and fixture files returns zero credential-shaped values. sowinsights and hops-mcp record nothing either.

So this control attaches to a testing practice, not to a repository. The two projects made the same trade differently and neither is wrong:

  • barley records real traffic — fixtures stay faithful to the live API, and every recorded byte is potential credential material. It leaked exactly once, through the one field nobody had listed.
  • hops hand-stubs at an interface — structurally immune to this leak, at the cost of fixtures that can drift from the real API with no test noticing.

The blueprint should therefore carry this as a conditional control: the question a new project must answer is not "which language is this?" but "does this project record real responses into committed files?" Copying barley's scrubber into hops would add maintained code that can never fire.

Two of our own controls collided — and the fix is the pattern

The fail-closed tests need credentials that are genuinely issuer-shaped, or they cannot prove the value patterns work. The secret-scan gate merged four days earlier flagged them, correctly. Resolved by weaving a NOTAREALTOKEN marker inside the span each rule captures and stopwording that one string — suppressed by value, never by path, so a real token in that same test file still fires. Path-allowlisting the test directory would have been faster and would have re-created the exact blind spot that made barley's own audit report a false PASS.

Methodology — repeatable for the next capability

  1. Inventory before scanning. Read what each repo already has (configs, CI, hooks, its own audits and accepted-risk registers) so findings are gaps, not rediscoveries.
  2. Same tool, same ruleset, same day. Cross-repo numbers are only comparable when the instrument is held constant — gitleaks 8.24.3 (the exact version the hops CI gate pins), default config for comparison, tuned config as a separate measurement.
  3. Full history, not working tree. A committed-then-deleted secret is still in every clone. Findings classified in-HEAD vs history-only — remediation differs (rotate + remove vs rotate).
  4. Triage by format confidence. High-confidence token formats (provider prefixes, PEM blocks) can't match by accident; loose regexes require manual review. Every reviewed with values masked; no credential tested for validity.
  5. Audit the audit. Every surprising audit verdict re-verified against the repo by hand — which is how three detector blind spots were found.
  6. Root-cause the control, not the leak. The cassette tokens were traced to the specific scrubber design (fail-open denylist), producing a transferable pattern, not a one-off fix.
  7. Prove a suppression is narrow before trusting it. Added in Phase 2, after a tuned scanner config was found suppressing real credentials. Any allowlist is diffed against a no-allowlist baseline, every suppressed finding must be attributable to a named entry, entries that match nothing are deleted rather than shipped, and synthetic positives are planted inside each suppressed context to confirm they are still detected. An untested suppression rule is indistinguishable from a disabled check.
  8. Resolve the real base ref before measuring. Also added in Phase 2, twice earned: two measurements were taken against local clones 5 and 229 commits stale. Every number now states the ref it was measured at, by SHA.
  9. Run every gate against the input it must fail on — absence included. Added in Phase 2, after our own hook scanner was found reporting "all clear" on a repo with no agent settings file at all: the skip-and-pass failure it had been written to correct. A gate is now proved with a planted positive, a negative control on real code, and an empty input, and its own source is placed inside the surface it protects.
  10. Close an item from the default branch, not from the branch that was reviewed. Also Phase 2: re-deriving the claims from main after merge is what showed the portable copy of a shipped checker was two commits stale — it still carried the fail-open version any second repo would have copied.
  11. Everything logged as it happens. Method log, findings, corrections (two of our own claims were caught and fixed by later evidence), and lessons — in the research repo, each number backed by a committed file.
