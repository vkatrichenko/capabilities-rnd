Gate Flow

Nearly half of AI-generated code ships with a vulnerability, and the rate is not falling with newer models. Gate Flow puts six deterministic gates at the five moments a change can go wrong — commit, agent call, merge, dependency update, audit — and proves each one against the input it must fail on.

What the untuned scanner costs

Point a secret scanner at a real repository with its default ruleset and 99.4% of what it reports is noise. Teams turn it off within a week. The craft is the tuned allowlist — verified false positives only, suppressed by value never by path, so a real token in an allowlisted file still fires. That tuning is a deliverable, not a setting.

What “declared” costs versus “enforced”

Across 26 repositories in one organisation, exactly one default branch required a passing status check before merge. Every gate that ever ran there reported a red cross that a merge could simply ignore. One org-level ruleset change is worth more than every individual gate — and it is where Gate Flow starts.

Layer 02Provectus gates
GATE 01 · SECRETS

Layered secret gate

commit → merge · unconditional

A fast advisory pre-commit scan on the developer machine, then a full-history scan in CI on every pull request with a tuned, value-level allowlist. Recorded test fixtures are deliberately not path-excluded — that is where the real credentials were.

Reads & writes
Staged files; full git history; allowlist config that cites each suppression's reason.
Where the engineer drives
Escape hatch on the local hook; none on the CI gate.
GATE 02 · AGENT

Agent-time guard

every agent tool call

A hook in front of each file or shell action the coding agent takes: it cannot read or write secret material at all, and it re-installs the local git hook after every session so “hook never installed” cannot happen on an agent's machine.

Reads & writes
Tool-call arguments; the repo's hook installation state.
Where the engineer drives
Sees the block and its reason inline; the agent does not retry.
GATE 03 · CODE

Deterministic SAST + evidence review

before commit · on merge

Static analysis with a quality gate on every merge request, plus a security review the agent runs on itself before commit. Every finding updates the instruction files, so the same class of bug is not generated twice.

Reads & writes
The diff; the CLAUDE.md / rules that steer future generation.
Where the engineer drives
Accepts, fixes, or records an accepted risk with reasoning.
GATE 04 · DEPENDENCIES

Dependency gate

any manifest or lockfile change

Three checks on every dependency diff: the package must exist on the registry and pre-date the pull request; the version must be older than a cooldown window; and the vulnerability audit runs on the change whether or not anyone labelled it.

Reads & writes
Manifests, lockfiles, registry metadata; blocks the PR.
Where the engineer drives
Trusted internal packages go on a named exclude list.
GATE 05 · TOOLCHAIN

Agent-config and toolchain gate

any change to the agent surface

Instruction files, hooks, skills and MCP configuration are declared security-sensitive, routed through CODEOWNERS, and scanned in CI — hooks resolved from settings, inline commands included. MCP servers must be pinned to a version, digest or commit. No surface to scan is itself a blocking finding.

Reads & writes
.claude/, .mcp.json, hook scripts, permission patterns.
Where the engineer drives
Owns the pin bump; review is binding.
GATE 06 · POSTURE

Posture ratchet

every PR · every merge to main

An independent scorecard, used as a per-check ratchet against a committed baseline rather than a score threshold: four checks fail a pull request if they drop, eight are reported, six are ignored with the reason recorded next to each. It fails closed when a check goes missing.

Reads & writes
Repo settings, workflows, branch protection; a baseline file.
Where the engineer drives
Raises the baseline; never lowers it silently.

Nothing here is exotic. Each gate is a small deterministic control wired into one stage of the workflow — and each is proved with a planted positive, a negative control on real code, and an empty input.

Calibration is the keystone

A control can exist, be enforced, be wired up — and still be scoped away by its own configuration.

We found four variants of the same failure in our own portfolio. A secret scanner whose allowlist matched whole lines, silently dropping any real token that shared a line with a suppressed value. An audit check that skipped the malicious-hook scan because hooks lived in a different directory — and reported 100%. A dependency cooldown that was a no-op because CI installed the package manager unpinned. A hook scanner we built to fix the skip-and-pass bug, which printed “all clear” on a repository with no settings file at all.

None of these was detected by the control itself, because a suppressed finding produces no signal. The blueprint therefore treats calibration as a deliverable with its own loop: every suppression config is diffed against a no-allowlist baseline, every suppressed finding must be attributable to a named entry, entries that match nothing are deleted, and synthetic positives are planted inside each suppressed context to prove the rule is narrow. An untested suppression is indistinguishable from a disabled check.

01 AUDIT12-dimension run on a cadence; every check carries evidence, a standard and a confidence tag.
02 VERIFYEvery surprising verdict — green ones most of all — is re-checked by hand against the repo.
03 FIXThe change cites the finding ID; the gate is run against a planted positive and an empty input.
04 INSTRUCTThe finding becomes a line in the instruction files, so the agent does not regenerate it.
05 RE-AUDITThe next run proves the score moved because the control did, not because the detector blinked.

Measured cadence in our own repos: 13 days from FAIL to PASS on the secret gate; two dimensions gained 14–16 points in 17 days.

Key use cases

Five moments an AI-assisted change goes wrong — and where the gate catches it.

UC-01

The credential in the test fixture

A recorded API response carries a runner-registration token the scrubber had no rule for. Header filtering worked; body filtering was a denylist. It sat in main for six months under a passing audit that skipped the tests directory.

Gate FlowGate 01 fires on the commit (fixtures are not path-excluded). The scrubber is inverted to fail closed — redact by key shape and by value shape — and a test reads every committed cassette so a future hole fails CI. Verified additive: 0 of 73 cassettes changed.
UC-02

The package that never existed

The agent suggests a plausible helper library. It is not on the registry — yet. By the time someone registers the name, the import is already in the codebase and the next install pulls whatever they published.

Gate FlowGate 04 blocks any newly added package the registry has never heard of, with age and near-neighbour thresholds derived from the manifest. Back-tested: 0 false positives across 21 packages added by 13 real commits, each judged as of its own commit date.
UC-03

The MCP server that updates itself

Every stdio MCP server in four repositories ran a mutable version — :latest, @canary, or a git URL with no ref. A compromised update executes with developer privileges at every session start. This is the “rug pull” in the OWASP Agentic Top 10.

Gate FlowGate 05 flags any unpinned launch in .mcp.json; servers are pinned to a digest, version or commit, and a pin bump is a reviewed change on the protected surface.
UC-04

The hook nobody parses

Four of the six agent hooks across the org existed only as inline shell strings inside a settings file — no linter reads them, no directory scan finds them, and the audit's malicious-hook check skipped them because it looked for a folder that was never there.

Gate FlowGate 05 resolves the hook surface from the settings file, never from a directory, and blocks download-and-execute, exfiltration, credential reads and guard tampering. Calibrated against the repo's own guard scripts: 0 hits on legitimate code, 24 self-tests inside the job, 13-second run.
UC-05

The control that is on and not binding

A repository requires a pull request and one approving review; administrators are exempt; 1 of the last 30 changesets carried an approval. Every earlier version of this finding was about a control being absent. This one was present, enabled and routed around.

Gate FlowGate 06 measures enforcement, not presence: branch-protection state is part of the ratchet, and a repository ruleset requiring the security jobs — with an empty bypass list — is the first change of the Enable phase.

The bet

Gates are cheap. Proof that they fire is the product.

The reading

Regulators, standards bodies and the model vendors themselves have converged: NIST SSDF, OWASP's CI/CD and Agentic Top 10, and Anthropic's own playbook all describe the same shape — deterministic scanners on every change, pinned toolchains, protected agent configuration, a recurring audit with a working remediation loop. The practices are settled. What is rare is a team that has measured its own.

The posture

Security tooling in most organisations is a property of a repository, never of the organisation. One repo hardened, three with nothing, is the normal shape — we measured it in our own portfolio before we measured it anywhere else. Gate Flow ports one reference implementation across the estate, then makes it binding at the org level.

The asymmetry

Adding a gate to five repositories cost a week. Running the same scorecard read-only across all 27 repositories cost an afternoon and produced the more valuable result: the one org-level setting that made every gate enforceable. Measurement first, then the cheapest change with the widest blast radius.

The window

Every unscanned commit is fresh exposure, and the AI-native vectors — agent permission allow-lists, hallucinated packages, self-updating MCP servers — are not on any conventional scanner's list yet. A team that installs the gates now has a verifiably clean history from that day. A team that waits has a history to remediate.

The risk

What we do not know. What we will not do.

What we don't know

The catch rate of the generation-time security review on your code is not measured until it runs on your code — on ours, a regex-only plugin caught 4 of 9 planted vulnerability classes and none of the Kotlin ones, which is why the built-in review is the gate and the plugin is a supplement. Which of your historical leaks are still live is unknown until the liveness probes run; we do not test credentials for validity without the owner in the room. And not every control is universal: the fail-closed fixture scrubber attaches to a testing practice — recording real API traffic — not to a language or a repository. The Sprint answers that question before anything is copied.

What we own

We do not rotate your credentials, sign off your releases or edit your production configuration. The engineer stays accountable for the change; the security owner holds the accepted-risk register; the platform admin applies the ruleset. Every gate ships with its self-tests inside the job, is proved against a planted positive and an empty input before it is called done, and places its own source inside the surface it protects. Every number we report states the commit it was measured at. Secret values never appear in any artifact we produce.

The organisation, cycle over cycle

Quarter over quarter
